# EMKE AI Marker Windows 桌面版设计规格

日期：2026-07-27  
状态：已完成对话确认，等待书面规格审核

## 1. 背景

当前仓库提供一个 Windows x64 Python/Tkinter 工具，用于为 JPG、JPEG、PNG
和 MP4 写入并严格验证：

```text
XMP-dc:Subject
└─ rdf:Bag
   └─ rdf:li = contains-synthetic-performer
```

现有实现具备递归扫描、保留原有 Subject、幂等追加、写后回读、原始 XMP
结构验证、只读验证、CSV 证据、单文件失败隔离和发布卫生检查。主要产品问题是：

- Tkinter 界面偏工程化，不能充分表达 EMKE 品牌。
- 输入依赖固定的“待标记”目录，不符合常见桌面拖放习惯。
- 默认直接修改原件且不创建备份，误操作成本高。
- 单一业务源文件同时包含领域逻辑、基础设施和 UI，长期维护困难。

PixPix 的浏览器工具证明了“免费合规工具”可以作为高意图入口，但它只支持
JPG/PNG，且没有展示当前仓库已有的严格 XMP 结构回读与证据记录。本项目借鉴其
低门槛单任务形式，不复制 PixPix 品牌、文案或资产。

## 2. 已确认的产品决定

- 交付形态：Windows x64 桌面应用。
- 技术路线：C#、.NET 10、WPF、MVVM，全原生重构。
- 产品名称：EMKE AI Marker。
- 首个 EMKE 品牌发行版本：`2.0.0`，不复用仓库现有 `v1.0.0` 标签。
- 支持格式：JPG、JPEG、PNG、MP4，扩展名不区分大小写。
- 默认安全策略：创建已标记副本，原件保持不变。
- 高级策略：允许覆盖原件，但必须显式开启并在每次运行前二次确认。
- 标记值固定为只读的 `contains-synthetic-performer`。
- 交付物：完整源码、测试和未签名的 Windows x64 自包含便携 ZIP。
- 首版界面语言：简体中文。字符串集中管理，为后续本地化保留结构；首版不包含
  其他语言包。
- 网络边界：媒体处理期间完全离线，不登录、不上传媒体、不发送遥测。

## 3. 非目标

首版明确不包含：

- AI 内容识别或“是否含 AI 人物”的自动判断。
- Amazon API 连接、上传后平台文件验证或审核保证。
- 法律意见或平台最终合规保证。
- 账号、云同步、远程任务、订阅、支付和遥测。
- 安装器、代码签名、自动更新和 Windows Store/MSIX 分发。
- ARM64 或非 Windows 平台版本。
- 用户自定义任意 XMP/IPTC 字段。

## 4. 架构

解决方案使用以下边界：

### 4.1 `Emke.AiMarker.App`

WPF 应用、窗口生命周期、拖放、文件选择、状态展示、命令和设置。采用 MVVM，
View 不直接调用 ExifTool 或文件系统。

### 4.2 `Emke.AiMarker.Core`

纯 C# 领域层，负责：

- 媒体发现、稳定排序与支持格式判断。
- 标记、只读验证和安全停止的任务编排。
- 输出策略、冲突策略和处理结果分类。
- 精确 Subject 匹配与严格 XMP 结构判定。
- 可序列化的进度、结果和证据模型。

Core 不依赖 WPF、具体 ExifTool 进程或 Windows UI。

### 4.3 `Emke.AiMarker.Infrastructure`

负责：

- ExifTool 子进程调用与 UTF-8 参数传递。
- 原件复制、临时文件、原子重命名和路径安全检查。
- Windows 重解析点、文件属性、单实例和目录打开。
- UTF-8 BOM CSV 记录与电子表格公式前缀防护。
- ExifTool 版本和运行时完整性检查。

### 4.4 `Emke.AiMarker.Tests`

包含领域单元测试、受控 ExifTool 集成测试、WPF ViewModel 状态测试、发布卫生测试
和从 Python 行为提取的契约向量。

### 4.5 旧 Python 实现

原 Python 实现不再进入产品运行时。它在 `legacy/python/` 中保留一个主要版本周期，
用于行为对照和回归追踪，并从发布 ZIP 中排除。

## 5. 数据流与文件安全

### 5.1 输入

用户可以拖入或选择多个文件、文件夹或两者的组合。扫描必须：

- 递归进入普通目录。
- 稳定排序。
- 去重相同规范化路径。
- 跳过不支持格式。
- 拒绝符号链接、联接点和其他重解析点。
- 单独报告无法访问的路径，不中断其他输入。

### 5.2 默认副本模式

1. 计算输出计划并检查输出目录是否可写。
2. 检查可用空间至少覆盖待复制文件总大小，并额外保留 5% 或 256 MB 中较大的
   安全余量。
3. 在最终输出所在目录创建应用专用临时文件；临时文件保留原媒体扩展名，以确保
   ExifTool 使用正确的容器处理逻辑。
4. 读取临时副本的现有 `XMP-dc:Subject`。
5. 仅在缺少精确目标值时追加目标标记。
6. 重新读取 Subject 与原始 XMP。
7. 确认目标值位于正式 Dublin Core 与 RDF namespace 下的
   `dc:subject/rdf:Bag/rdf:li`。
8. 验证通过后将临时文件原子重命名为最终副本。
9. 失败时删除临时文件，原件保持不变。

默认输出目录位于每个顶层输入旁，名称为 `EMKE 已标记`。文件夹输入保留相对目录
结构。多个顶层输入不会互相覆盖。

### 5.3 目标冲突

应用绝不静默覆盖现有输出：

- 若目标文件已经严格合规，记录“输出已存在且合规”并复用。
- 若目标文件存在但未严格合规，记录“目标冲突”，不写入该路径。
- 用户可以清空冲突目标、修改输出目录或调整目标文件名后重新运行。直接修改原件
  的高级模式不作为输出冲突的自动解决方式。

### 5.4 高级覆盖原件模式

高级设置中的“直接修改原件”默认关闭。开启后：

- 主界面的安全提示变为警告色并明确说明不会创建备份。
- 每次运行都显示文件数量、不可恢复风险和确认按钮。
- 已合规文件不重复写入。
- 写入后仍执行同样的严格回读。
- 单个失败不影响其他文件。
- 可以要求 ExifTool 尽量保留修改时间，但界面和文档不得保证所有文件系统时间、
  属性或容器校验值保持不变。

### 5.5 安全停止

用户点击“安全停止”后：

- 当前文件完成复制、写入和验证闭环。
- 不再开始下一个文件。
- 已成功的输出保留。
- 未开始文件记录为“用户停止前未处理”。
- CSV 仍然生成，明确记录停止原因。

## 6. 单页界面

主窗口使用紧凑单页结构，不使用向导或侧边导航。

### 6.1 空状态

- 标题栏显示真实 EMKE Logo、`EMKE AI MARKER`、本地处理状态和设置入口。
- 主区显示用途说明、隐私提示和大面积拖放区。
- 支持点击选择文件或文件夹。
- 显示支持的四种格式。

### 6.2 已选择状态

- 显示文件数量、总大小、可处理数量和跳过数量。
- 详细文件列表默认折叠，可按需展开。
- 标记值只读显示。
- 默认输出路径清晰可见，并可更换。
- 主按钮显示将处理的文件数量。

### 6.3 处理状态

- 输入与设置在运行期间锁定。
- 显示总体进度、当前文件和四类累计结果。
- 主操作切换为“安全停止”。
- 窗口关闭操作提示用户先安全停止；不强制杀死当前 ExifTool 进程。

### 6.4 完成状态

显示：

- 新增并验证通过。
- 原本或输出已合规。
- 失败。
- 跳过或停止前未处理。

提供“打开输出文件夹”“查看 CSV 记录”和“重新开始”。

“只读验证”是主界面的次级按钮。它不写媒体，但允许创建 CSV 运行记录。

## 8. 错误处理与恢复

启动前检查：

- ExifTool 存在、版本匹配且安装清单未被篡改。
- 输出目录可写。
- 可用空间满足输出计划。

每个文件拥有独立结果。错误信息必须包含用户能采取的下一步，例如更换输出目录、
关闭占用程序或处理目标冲突。

应用只能清理自己命名空间下的临时文件。下次启动时可以清理上次异常退出留下的
应用临时文件，但不得删除用户原件或无法确认归属的文件。

CSV 记录包含相对路径、格式、运行模式、处理状态、验证结果、验证字段、实际读取
值、XMP 结构、验证时间、ExifTool 版本和错误原因。任何可能被电子表格解释为公式
的单元格必须转义。

## 9. 测试

### 9.1 契约测试

覆盖：

- Subject 完整字符串、区分大小写匹配。
- `dc:subject/rdf:Bag/rdf:li` 与正式 namespace。
- 错误的 Seq、namespace、缺失或损坏 XMP。
- 保留已有 Subject 和重复运行幂等。
- 中文、空格、括号和大小写扩展名。
- 递归扫描、稳定排序、重解析点拒绝。
- CSV 列结构、UTF-8 BOM、原子写入和公式前缀防护。
- 单文件失败隔离和安全停止。

### 9.2 ExifTool 集成测试

使用仓库自建、无私人内容的受控 JPG、JPEG、PNG、MP4 fixture。验证：

- 默认模式下原件字节哈希不变。
- 输出副本包含目标 Subject。
- 原始 XMP 结构严格通过。
- 现有 Subject 被保留。
- 媒体像素或视频流在受控 fixture 中没有被重新编码。

运行时不对每个真实媒体计算完整媒体流哈希，也不向用户宣称逐文件像素或视频流
哈希验证。

### 9.3 UI 与状态测试

覆盖空状态、拖放、选择汇总、折叠详情、只读验证、处理中、安全停止、完成、失败、
输出冲突、高级覆盖开关和二次确认。

### 9.4 发布测试

Windows CI 必须：

1. 运行全部测试。
2. 发布 `win-x64` 自包含应用。
3. 执行无界面启动自检。
4. 检查 ZIP 白名单、许可证、Logo、ExifTool 与隐私卫生。
5. 拒绝媒体、CSV、源码缓存、日志、绝对本机路径和临时文件进入发布包。
6. 生成确定性 ZIP 和 `SHA256SUMS.txt`。

## 10. 交付与证据边界

便携 ZIP 包含：

- EMKE AI Marker 可执行文件和 .NET 自包含运行时。
- 锁定版本的 ExifTool。
- 应用 Logo 与运行所需资源。
- 使用说明、MIT License、第三方许可证和 notices。
- 空的示例输出结构，不含媒体或运行记录。

首版不签名，文档必须明确说明 SmartScreen 可能出现提示。

以下证据必须分开报告：

- 单元测试通过。
- Windows CI 构建通过。
- ZIP 结构与 SHA-256 验证通过。
- Windows 11 x64 真实电脑启动通过。
- 使用受控 JPG、JPEG、PNG、MP4 的真实处理冒烟通过。

CI 和打包通过不能替代真实电脑、SmartScreen、文件选择器、拖放、资源显示或
ExifTool 实际运行验收。公开交付前必须完成 Windows 11 x64 启动和四种格式的受控
冒烟测试。

## 11. 验收标准

首版完成必须同时满足：

1. 用户可以拖放或选择 JPG、JPEG、PNG、MP4 文件与文件夹。
2. 默认模式下原件字节不变，合规副本写入目标目录。
3. 严格验证精确 Subject 与正式 XMP Bag/li 结构。
4. 已有 Subject 保留，重复运行不追加重复值。
5. 单文件失败不终止批次，安全停止不留下半成品。
6. 只读验证不写媒体，只生成本地结果和 CSV。
7. Logo、`#36A39E`、单页布局和确认的文案层级正确呈现。
8. 所有自动化测试、Windows CI、发布卫生和 SHA-256 检查通过。
9. Windows 11 x64 真实电脑完成启动和四种格式冒烟。
10. 便携 ZIP 不包含私人媒体、运行记录、缓存、临时文件或本机绝对路径。
